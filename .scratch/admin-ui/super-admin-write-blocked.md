**Summary:** Super admin API keys receive 403 on all write operations (create/update/delete) for blueprints, affixes, and global meta attributes, making the admin UI read-only.

Super admin API keys should be able to perform write operations by specifying a `client_id` query parameter (similar to how read operations work). The generated API client should pass the UI store's `selectedClientId` with write requests.

- The `resolve_client_id_for_write` function in `blueprints.rs`, `affixes.rs`, and `global_meta_attributes.rs` — needs to accept an optional `client_id` parameter for super admins
- The ArcheClient's request methods in the generated client — needs to pass `selectedClientId` as a query parameter on write requests
- The UI store's `selectedClientId` — already exists in `ui.ts` but is never sent to the API

## Bug Description

The Arche API service intentionally blocks super admin API keys from performing write operations (create, update, delete) on blueprints, affixes, and global meta attributes. The `resolve_client_id_for_write` function in the API service returns a 403 Forbidden error for super admin users, preventing them from specifying a client context for write operations.

However, the admin UI is designed to be used with the super admin API key (the only key entered at login). This means **the entire CRUD functionality of the admin UI is broken** — users cannot create, edit, or delete any resources through the UI.

## Steps to Reproduce

1. Log in to the admin UI with a super admin API key (e.g., `arche_k_a7q5p2gxbQBbV2XxHG8YP0lTAxPNYNpprdAwtFBHROIuPgAb`)
2. Navigate to any list page (Blueprints, Affixes, Global Meta Attributes)
3. Click "Create" button
4. Fill in the form and submit

**Expected:** The resource is created successfully.

**Actual:** A 403 error is returned: `"Super admin must specify a client context for write operations"`. The UI either shows an error toast or silently fails.

## Root Cause

The `resolve_client_id_for_write` function in three locations does not accept a `client_id` query parameter (unlike the read function `resolve_client_id` which does):

- `crates/arche-service/src/blueprints.rs:715`
- `crates/arche-service/src/affixes.rs:63`
- `crates/arche-service/src/global_meta_attributes.rs:61`

For comparison, the read function `resolve_client_id` accepts a `query_client_id: Option<Uuid>` parameter that allows super admins to scope read operations to a specific client. The write function needs a similar mechanism.

## Impact

- Users cannot create blueprints, affixes, or global meta attributes
- Users cannot edit or delete existing resources
- The entire admin UI is read-only for super admins
- Only client-scoped API keys (created via the API directly) can perform write operations
- This breaks PRD user stories #8, #11, #13, #15, #16, #17, #19, #21, #22, #25, #27

## Suggested Fix

Add a `client_id` query parameter (or `X-Client-Id` header) to the write handlers and pass it to `resolve_client_id_for_write`. One approach:

1. Extract `client_id` from query parameters in the create/update/delete handlers
2. Pass it to a modified `resolve_client_id_for_write` that, for super admins, returns the specified `client_id` (returning an error if none provided)
3. Update the generated API client to pass the selected client ID from the UI store
